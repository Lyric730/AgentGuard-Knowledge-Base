# 第一阶段 SOP：站点摸底与技术 SEO 基线

对应 AgentGuard 周期：2026-07-03 至 2026-07-09

## 这周要解决什么

先弄清客户现在有什么，再谈关键词和内容。

这周结束时，执行人员应该能回答：

- 客户的正式网站和主要市场是什么？
- 网站现在有哪些公开页面，哪些页面应该被搜索引擎看到？
- 当前最影响后续 SEO 的问题是什么？
- 哪些产品能力有公开证据，可以写进页面？
- 哪些数据或权限还没拿到，因此暂时不能下结论？

## 开始前要准备什么

- 客户官网、旧域名和可能存在的子域名。
- 产品介绍、公开文档、帮助中心、价格页、GitHub 或其他一手资料。
- 目标国家和语言。
- 客户已经知道的主要竞品。
- 如果能提供，补充 GSC、GA4、CMS、网站源码或日志权限。没有也可以先做公开检查，但要写清检查边界。

## 一步步怎么做

### 第一步：确认客户和项目边界

和客户确认最终使用的品牌名、正式域名、目标市场、目标语言、主要用户和本轮业务目标。

如果客户自己也没确定最终域名或产品定位，先把它列成待确认项。不要在后续页面里自行替客户做决定。

### 第二步：收集客户的一手资料

把官网、产品文档、帮助中心、公开仓库、价格说明、隐私说明和客户提供的材料统一归档。

从这些材料里整理一份产品事实表。每条事实都保留来源，并区分：

- 已公开、可以直接使用的事实。
- 客户口头提过，但还没有正式证据的内容。
- 明确不能写的夸张承诺、未上线能力和未确认数字。

这份表以后会给页面策划、Brief、正文和 QA 反复使用。

### 第三步：列出现有页面

从导航、sitemap、站内链接和公开搜索入口收集当前 URL。记录页面标题、页面用途、语言、是否能打开，以及它大致属于产品页、解决方案页、文档页还是内容页。

这一步的目的不是马上重写页面，而是先知道哪些页面已经存在。后面的关键词规划必须先给现有页面找位置，再决定是否新建页面。

### 第四步：做技术 SEO 检查

检查搜索引擎能否正常访问网站，以及网站有没有给出互相冲突的信号。至少要看：

- 域名跳转、canonical、sitemap 和 robots 是否指向同一个正式域名。
- 应该收录的页面能否访问，登录后或私有页面是否被错误公开。
- 每页的 Title、Description、H1 和语言是否一致。
- 移动端加载、内部链接、结构化数据和多语言设置是否有明显问题。
- 公开页面和浏览器最终看到的页面内容是否一致。

有 GSC、GA4 或日志权限时，再补客户自己的收录、曝光、点击、转化和抓取情况。没有这些权限，不要假装已经判断过。

### 第五步：把问题按处理顺序写清楚

先写会影响全站的事情，例如正式域名、抓取和收录；再写单页标题、结构化数据、性能等问题。

每个问题都要写：

- 现在看到的现象。
- 为什么会影响后续工作。
- 谁比较适合处理。
- 应该怎么改。
- 改完后怎么确认真的解决了。

不要只给客户一张问题清单。客户要能把报告直接拆成任务。

## 这周会得到哪些产出

| 产出 | 里面要有什么 | 谁会继续用 |
|-|-|-|
| 技术 SEO 客户报告 | 结论、优先级、详细问题、负责人、修复建议、验收办法、权限缺口 | 客户负责人、网站负责人、后续 SEO 执行 |
| 当前站点页面清单 | URL、页面类型、当前状态、是否应保留、是否需要修改 | 关键词规划、网站架构、内容规划 |
| 产品事实表 | 可用事实、来源、限制、未确认项 | Brief、页面文案、Blog、事实 QA |
| 项目待确认清单 | 域名、市场、定位、权限和负责人 | 客户和项目负责人 |
| 下一阶段交接说明 | 哪些资料已经确认，哪些页面和问题会影响竞品与关键词研究 | 第二阶段执行人员 |

## 同一批资料还能支持什么

- 现有 URL 会进入后面的 URL Map，帮助判断“改旧页”还是“建新页”。
- 产品事实表会限制页面和文章中的产品表述，避免越写越大。
- 技术问题会变成网站页面上线前的检查项。
- 目标市场和语言会决定 DataForSEO 的查询范围，不能等数据拉完才改市场。

## 什么情况下不能进入下一阶段

- 最终域名或目标市场仍完全不明确。
- 客户产品是什么、面向谁、主要能力是什么都没有可信资料。
- 公开网站完全无法读取，客户也不能提供任何页面清单。
- 会影响整个项目方向的待确认项没有负责人。

如果只是缺少 GSC、GA4 或源码权限，可以进入公开竞品和关键词调研，但必须在报告里保留数据缺口。
